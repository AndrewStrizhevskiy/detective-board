# Удалённый доступ к GPU-серверу (SSH через университетский VPN)

Для кого: участники команды, которым нужно работать на сервере удалённо. Что делать на самом сервере (извлечение,
обучение, отчёты), описано в [SERVER_GUIDE_RU.md](SERVER_GUIDE_RU.md) и [SERVER_RUNBOOK.md](SERVER_RUNBOOK.md).
Здесь только путь до сервера: сеть, VPN, ключи, правила общей машины и разбор поломок.

Проверено 2026-10-29 из сети университета: вход по ключу работает. **Через университетский VPN сервер в тот же день
не ответил** (см. раздел 6): способ 4.2 пока не подтверждён, не рассчитывайте на него без проверки.

## 2. Что нужно получить (один раз)

1. **Логин и пароль университета** для VPN. Свои собственные. Чужие не использовать, в репозиторий и в чаты не писать.
2. **Файл `.ovpn`** от техподдержки университета (тот же, что получил лид). Правила: положить в `~/vpn/` с правами `600`,
   в репозиторий не добавлять (внутри ключевой материал), друг другу не пересылать, пока ИТ не разрешат это явно.
3. **Свой SSH-ключ** и добавление его на сервер (раздел 3).
4. Права на сам сервер: доступ выдаёт лид. Без добавленного ключа сервер вас не пустит (это нормально).

Пакеты на Linux: `sudo apt install openvpn openssh-client`. На macOS подойдёт Tunnelblick или `brew install openvpn`,
на Windows OpenVPN GUI; ssh встроен в PowerShell (`ssh user@195.19.35.82`).

## 3. SSH-ключ

У каждого свой ключ. Приватный файл (`id_ed25519`) никому не отправлять и на сервер не копировать.

```bash
ssh-keygen -t ed25519 -C "ваше-имя-на-github@detective-board" -f ~/.ssh/id_ed25519_dbserver
```

Лиду уходит только публичная часть:

```bash
cat ~/.ssh/id_ed25519_dbserver.pub
```

Лид добавляет ключ (с компьютера, который уже входит на сервер) и сразу проверяет вход:

```bash
{ echo; cat colleague.pub; } | ssh user@195.19.35.82 'cat >> ~/.ssh/authorized_keys'
```

Имя в комментарии ключа нужно, чтобы потом понимать, чей он, и отзывать по одному.

Удобный алиас в `~/.ssh/config`:

```
Host dbserver
    HostName 195.19.35.82
    User user
    IdentityFile ~/.ssh/id_ed25519_dbserver
    IdentitiesOnly yes
    ServerAliveInterval 30
    ServerAliveCountMax 4
```

После этого вход: `ssh dbserver`.

## 4. Подключение

### 4.1. Из сети университета (Wi-Fi или кабель)

VPN не нужен.

```bash
scripts/server_access_check.sh
ssh dbserver
```

### 4.2. Из дома или из другой сети

Шаг 1. Поднять VPN университета и **оставить это окно открытым**:

```bash
sudo openvpn --config ~/vpn/bmstu.ovpn --pull-filter ignore redirect-gateway --verb 3
```

`--pull-filter ignore redirect-gateway` оставляет остальной интернет как был: через VPN идут только сети университета.
В конце лога должна быть строка `Initialization Sequence Completed`. Спросит логин и пароль университета.

Шаг 2. В другом терминале:

```bash
ip route get 195.19.35.82        # в строке должно быть "dev tun0"
scripts/server_access_check.sh   # четыре шага, все OK
ssh dbserver
```

Шаг 3. По окончании работы в окне с VPN нажать Ctrl+C.

Если в `.ovpn` стоит имя `openvpn.bmstu.ru`, а дома это имя не находится (DNS провайдера не знает внутреннее имя или
подменяет ответ), заменить его на IP шлюза, который покажет `getent hosts openvpn.bmstu.ru`, выполненный в
университете. У лида для этого отдельная копия файла с IP.

### 4.3. Если на компьютере уже работает VPN или прокси в режиме TUN (sing-box, clash, v2ray, WireGuard)

Это самая частая причина "странных" ошибок (раздел 5). Что нужно:

1. Университетский VPN должен выиграть маршрут к 195.19.32.0/19. Проверка: `ip route get 195.19.35.82` показывает `dev tun0`.
2. Трафик к шлюзу VPN (UDP 2100) не должен ломаться самим прокси. Если соединение с шлюзом не поднимается, добавьте в
   прокси правило "напрямую" для адреса шлюза и UDP 2100.
3. Диагностику вести **не через `nc -vz`/`telnet`**: TUN-прокси сам отвечает на рукопожатие любого адреса (раздел 5).
   Использовать только `scripts/server_access_check.sh` (баннер SSH и вход по ключу).

## 6. Что точно известно, а что нет

Известно: 2026-10-29 доступ по ключу из сети университета работает (баннер `SSH-2.0-OpenSSH_10.0p2 Debian-7`, вход, GPU виден,
`ollama serve` запущен).

**Через VPN не работает (2026-10-29 15:40, ноутбук лида в другой сети, VPN поднят, `tun0` с адресом 172.16.160.126, маршрут к серверу
идёт через `tun0`):** ping и SSH до 195.19.35.82 без ответа; в `tun0` уходят пакеты, обратно почти ничего. При этом сам VPN
исправен: пинг-проверка 195.19.34.0/24 через него даёт около 90 живых адресов. В 195.19.35.0/24 (сети сервера) не отвечает **ни один**
адрес, включая шлюз. Вывод (нужно подтвердить: в тот же момент кто-то из сети университета должен увидеть сервер живым): из пула адресов VPN (172.16.160.x) сеть 195.19.35.0/24 не достижима. Причина на стороне университета
(правило фильтрации или другой путь), у нас её исправить нельзя. В наших записях за 2026-10-28 нет ни одного подтверждённого входа
на сервер через VPN.

Подсказка: на сервере в `authorized_keys` есть ключ `jump@science-iu5`, а в `last login` в феврале стоит адрес 172.16.192.4. Похоже,
штатный путь идёт через промежуточный узел кафедры. Это предположение, нужно спросить техподдержку.

Не проверено: поведение VPN при двух одновременных сессиях под одной учётной записью, работа с macOS и Windows. Первому, кто проверит из дома,
записать результат сюда.

## 7. Если не работает: порядок проверки

1. `scripts/server_access_check.sh`: смотрите, на каком шаге остановилось.
2. Шаг 1 показывает не `tun0` вне университета: VPN не поднят или не выиграл маршрут (раздел 4.3).
3. Шаг 3 (баннера нет), VPN поднят: сервер выключен или недоступен. Написать лиду.
4. Шаг 4 `Permission denied`: сервер достижим, ключ не добавлен или не тот. `ssh -v dbserver` покажет, какие ключи предлагаются.
5. Лог VPN: `Initialization Sequence Completed` нет, строка `AUTH_FAILED`: логин или пароль университета.
6. Лог VPN: бесконечно `TLS handshake failed` или `Connection timed out`: до шлюза не доходит UDP 2100 (прокси или сеть).
7. Ничего не помогло: приложить вывод `scripts/server_access_check.sh` и `ip route get 195.19.35.82` в issue или в чат.
   Пароли, содержимое `.ovpn` и приватные ключи не прикладывать.

## 8. Правила общей машины

Сервер общий, учётка одна. Поэтому:

- Перед запуском тяжёлого: `timeout 10 nvidia-smi`, `ps -eo pid,etime,user,cmd | grep -E "[p]ython|[o]llama"`, и напишите в чат команды,
  что запускаете. Одновременно одна задача на GPU (12 ГБ).
- Работайте в своей папке `~/work-<имя>`, чужие не трогать. Долгие задачи запускать через `nohup ... > лог 2>&1 &`
  (tmux на этой машине не оказался надёжным).
- `ollama serve` на сервере запущен один на всех. Не перезапускать и не убивать без согласования. Если нужна другая версия
  или параметры, спросить лида.
- Не оставлять на сервере токены GitHub, приватные ключи, пароли университета; не запускать `gh auth login`.
- Не ставить VPN и любое ПО сверх согласованного (`uv`, Ollama и то, что лид одобрил).
- Результаты забирать на свой компьютер сразу (`rsync -av dbserver:~/work-имя/результаты/ ./`), диск 64 ГБ и общий.
- Работа вне проекта на этой машине запрещена.
- Кончили: убедиться, что ваши процессы остановлены (`ps -u user`), временные файлы удалены.

## 9. Для лида: выдача и отзыв доступа

- Выдать: команда из раздела 3. Проверить, что вход работает: `ssh -i ключ user@195.19.35.82 true`.
- Отозвать: на сервере удалить из `~/.ssh/authorized_keys` строку с нужным комментарием. Посмотреть список без самих ключей:
  `awk '{print NR": "$1" "$NF}' ~/.ssh/authorized_keys` (номер строки, тип ключа, комментарий).
- Если администратор университета разрешит отдельные учётки, перейти на них и убрать общий `user`.
